Archipelago Broadcast Control v0.3.7

The HTTP API provides state and graphics data, plus authenticated player status updates. The WebSocket API provides real-time state and production control.

HTTP endpoints

Read-only API endpoints accept GET and HEAD. Player status control uses POST /api/player/status. JSON API responses use Cache-Control: no-store. Lower-third endpoints also allow cross-origin reads.

EndpointResponse
GET/api/configPublic event configuration, with player tokens removed.
GET/api/stateComplete current production state.
GET/api/lower-thirdsGraphics-friendly data for all configured players.
GET/api/lower-thirds/liveThe current live player, or player: null.
GET/api/lower-thirds/{playerId}Graphics-friendly data for one player. Unknown IDs return 404.
GET/healthBasic health/discovery data including player count and WebSocket path.
POST/api/player/statusSet the authenticated player's production status using a bearer token.

Player status control

POST /api/player/status is intended for simple player-side integrations that cannot keep an authenticated WebSocket connection open, such as Stream Deck HTTP-request actions.

POST /api/player/status
Authorization: Bearer PLAYER_TOKEN
Content-Type: application/json

{"status":"asap"}

The token identifies the player. status accepts normal, soon, asap, or downtime. A successful request returns the updated player state and broadcasts the same state change to connected WebSocket clients.

Atomic player update

admin.player.update validates every supplied field before changing state. If any field is invalid, nothing is applied.

{
  "type": "admin.player.update",
  "data": {
    "playerId": "john",
    "currentGame": "TUNIC",
    "status": "asap",
    "airState": "standby"
  }
}

Important behavior

  • A game change resets the player's status to Normal and clears status timing and ASAP acknowledgement.
  • Setting a status starts a fresh request using that status's configured expiration time.
  • Only one player can be live at a time.
  • Taking an active ASAP request live records its acknowledgement.
  • admin.player.clear preserves current game and air state.
  • admin.player.panic preserves current game but sets the player off-air and Normal.
  • admin.event.reset preserves current-game selections and connection state, while clearing transient production state and returning compact mode to priority.
  • Compact mode accepts calls as an alias for priority, and downtime as an alias for bk.

Bitfocus Companion

Connect a Generic WebSocket connection to ws://SERVER-IP:3000/ws. Reading state does not require authentication. Production commands require auth.admin.

Every server WebSocket message includes flat per-player fields at the top level for simple Companion feedbacks:

{
  "andy_status": "asap",
  "andy_air": "off",
  "andy_game": "A Link to the Past",
  "andy_connected": true
}

The key uses the configured player ID, so Companion can use a JSON Path such as andy_status without array indexes. Available suffixes are _status, _air, _game, and _connected.

To send production commands, authenticate once on the same persistent connection:

{"type":"auth.admin","data":{"key":"YOUR_ADMIN_KEY"}}

After authentication, the admin messages above can be sent directly from Companion actions.

Graphics

Polling graphics can use the lower-third HTTP endpoints. Integrations that need immediate updates can listen for state.snapshot over WebSocket.
