Archipelago Broadcast Control

Complete API Reference

HTTP and WebSocket interfaces for player state, lower thirds, production control, compact monitor modes, and broadcast automation.

Server Version: v3.4HTTP / JSONStandard WebSocket / JSON

Overview

Archipelago Broadcast Control exposes a read-only HTTP API and a bidirectional WebSocket API.

HTTP APIBest for graphics systems, monitoring, polling, configuration discovery, and simple read-only integrations.
WebSocket APIBest for real-time state updates, player controls, production controls, Bitfocus Companion, and automation.

Version 3.4 adds admin-side control of player status, current game, and atomic multi-field player updates, in addition to the existing air-state controls.

HTTP API Behavior

API endpoints accept GET and HEAD. Other HTTP methods return 405 Method Not Allowed with Allow: GET, HEAD.

JSON responses include:

Content-Type: application/json; charset=utf-8
Cache-Control: no-store

Lower-third endpoints additionally include:

Access-Control-Allow-Origin: *

CLIENT → SERVERadmin.player.air

Sets a player's air state. Requires admin authentication.

{
  "type": "admin.player.air",
  "data": {
    "playerId": "alan",
    "airState": "live"
  }
}

Valid values: off, standby, live.

  • Only one player may be live at a time.
  • Taking an active ASAP request live records asapTakenLiveAt.

CLIENT → SERVERadmin.player.status

Sets a player's production status directly. Requires admin authentication.

Request

{
  "type": "admin.player.status",
  "data": {
    "playerId": "alan",
    "status": "soon"
  }
}

Valid Status Values

normal
soon
asap
downtime

Behavior

  • Uses the same configured expiration duration as a player-originated status change.
  • Sets a fresh statusSetAt timestamp for non-normal statuses.
  • Calculates statusExpiresAt from the configured timeout.
  • Clears asapTakenLiveAt, making a newly assigned ASAP status a fresh production request.
  • Persists state and broadcasts one new state.snapshot.

CLIENT → SERVERadmin.player.game

Changes a player's current game. Requires admin authentication.

Request

{
  "type": "admin.player.game",
  "data": {
    "playerId": "alan",
    "game": "Celeste"
  }
}

Validation

The game must appear in that player's configured games array.

Behavior

This intentionally mirrors the player-side player.game behavior:

  • Sets currentGame.
  • Resets status to normal.
  • Clears statusSetAt and statusExpiresAt.
  • Clears asapTakenLiveAt.
  • Persists state and broadcasts one new state.snapshot.

CLIENT → SERVERadmin.player.update

Atomically updates one or more supported player fields. Requires admin authentication.

Request

{
  "type": "admin.player.update",
  "data": {
    "playerId": "alan",
    "currentGame": "Super Metroid",
    "status": "asap",
    "airState": "standby"
  }
}

Supported Fields

FieldTypeValidation
playerIdStringRequired; must identify a configured player.
currentGameStringOptional; must be assigned to that player.
statusStringOptional; must be a configured status.
airStateStringOptional; must be off, standby, or live.

Atomic Validation

All requested fields are validated before any state is changed. If one supplied field is invalid, none of the requested changes are applied.

Order of Application

  1. If currentGame is supplied, the game is changed first and the previous status/ASAP acknowledgement is cleared.
  2. If status is also supplied, that status is then applied as a fresh status request.
  3. If airState is supplied, it is applied last, including the one-live-player rule and ASAP acknowledgement behavior.

Example: Change Game and Immediately Request ASAP

{
  "type": "admin.player.update",
  "data": {
    "playerId": "alan",
    "currentGame": "TUNIC",
    "status": "asap"
  }
}

The resulting state is currentGame: "TUNIC" with a fresh asap request, despite game changes normally resetting status.

Example: Prepare a Player for Air

{
  "type": "admin.player.update",
  "data": {
    "playerId": "alan",
    "status": "soon",
    "airState": "standby"
  }
}

Broadcast Behavior

A successful atomic update persists once and emits a single resulting state.snapshot, avoiding intermediate states from multiple separate commands.

Heartbeat & Reconnection

The server uses WebSocket ping/pong heartbeat handling to detect dead clients. New connections must re-authenticate before issuing protected commands.
